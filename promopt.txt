- Spring Boot backend ya existente para bodegas, productos, movimientos
- Base de datos: **PostgreSQL en Supabase** (nube) - esquema `proyecto`
- Pruebas: H2 con modo PostgreSQL - esquema `PUBLIC`
- Ya se fixeó el campo pdfBytes con `columnDefinition = "bytea"` SIN `@Lob` para evitar errores de Large Object en Supabase
- Seguridad JWT ya implementada con roles: ADMIN, EMPLEADO, AGENTE
- Puertos: 8080 (backend), 3000 (frontend posible)

# OBJETIVO DEL MCP (PostgreSQL/Supabase aware)
Crear un servidor MCP pequeño que sea capa de intermediación entre n8n y la API REST del backend Spring Boot. Considerando Supabase:

- **NO accede directamente a la base de datos** - usa la API REST
- **NO implementa reglas de negocio** - solo llamadas a endpoints
- **Autenticación con rol AGENTE** - las herramientas deben usar un usuario con rol AGENTE en Spring Security
- Compatible con la configuración actual de SecurityConfig.java

# HERRAMIENTAS OBLIGATORIAS (6 exactamente)

Todas las herramientas usan GET/POST sobre los endpoints ya definidos en el proyecto Spring Boot:

1. **consultar_stock_producto(productoId)** 
   - Endpoint: `GET /productos/{id}/stock`
   - Parámetro: productoId (Long)
   - Retorna: stock actual y detalles del producto
   - Consideración Supabase: compatible con la configuración actual

2. **consultar_bodegas_criticas()**
   - Endpoint: `GET /bodegas/criticas`
   - Retorna: bodegas con ocupación >= 90%
   - Fórmula: (unidades / capacidad) × 100 >= 90

3. **consultar_productos_en_riesgo()**
   - Endpoint: `GET /productos/riesgo`
   - Retorna: lista productos con stock below punto de reorden
   - Incluye para cada: productoId, nombre, proveedorId, stockTotal, consumoDiarioPromedio, puntoReorden, diasCobertura, estadoCobertura, bodegaDestinoId
   - La bodegaDestinoId sugerida es la bodega con menor stock de ese producto (empate -> menor id)

4. **consultar_kpis()**
   - Endpoint: `GET /kpis`
   - Retorna los 4 indicadores con estructura exacta:
     {
       "calculadoEn": "2026-08-24T06:00:00-05:00",
       "ocupacionPorBodega": [{ "bodegaId": 1, "nombre": "Bogota", "porcentaje": 92.5 }],
       "productosEnQuiebre": 1,
       "productosEnRiesgo": 2,
       "ordenesPorAprobar": { "cantidad": 1, "montoTotal": 45000.0 },
       "movimientosAyer": { "entrada": 2, "salida": 3, "transferencia": 1 }
     }

5. **crear_orden_borrador(productoId, proveedorId, bodegaDestinoId, cantidad, precioUnitario)**
   - Endpoint: `POST /ordenes`
   - Crea una orden en estado BORRADOR
   - El servidor calcula total (cantidad × precioUnitario)
   - Retorna la orden creada con todos los campos
   - Consideración: el campo bodegaDestino es OBLIGATORIO

6. **publicar_resumen(resumen)**
   - Endpoint: `POST /panel/resumen`
   - Valida y publica un resumen estructurado
   - JSON contrato exacto con fecha, narrativa, alertas, accionesSugeridas
   - Retorna el último resumen guardado o 404 si no existe

# RESTRICTIONES OBLIGATORIAS (CRÍTICAS)

## 1. Sin herramienta de aprobar órdenes
- **Esta es una restricción obligatoria**: No existe una herramienta para aprobar órdenes en el MCP
- El flujo n8n tampoco debe poder aprobar órdenes
- Esta restricción está en el archivo SKILL.md también
- El AGENTE no puede aprobar (retorna 403) - ya protegido en SecurityConfig

## 2. Autenticación con rol AGENTE
- Todas las herramientas MCP deben autenticarse como usuario con rol **AGENTE**
- En SecurityConfig ya tengo: `.requestMatchers(HttpMethod.GET, "/api/kpis").hasAnyRole("ADMIN", "AGENTE", "EMPLEADO")` etc.
- El MCP debe usar credenciales de un usuario AGENTE (no admin, no empleado)
- Probar: AGENTE intenta aprobar orden → 403 Forbidden

## 3. Sin conexión directa a mi SQL/PostgreSQL
- El MCP NUNCA debe tener JDBC connections, queries directas, o acceso a tablas
- Toda comunicación es SOLO mediante la API REST HTTP
- El MCP es solo una capa de enrutamiento/transformación de requests

## 4. Compatibilidad Supabase (bytea sin @Lob)
- El campo pdfBytes en OrdenCompra ya tiene `columnDefinition = "bytea"` SIN `@Lob`
- Esto evita el error "Value too long for column PDF_BYTES BINARY VARYING(255)" que fallaba en Supabase
- El MCP al generar/leer PDFs debe esperar este tipo de dato en la API
